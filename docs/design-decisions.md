# 设计决策记录

> 记录「为什么这么设计」以及踩过的坑。每条格式：**背景 → 决策 → 理由 → 权衡**。
> 面试前通读一遍 —— 这里是可以主动讲的深度点。

---

## 1. 业务错误也返回 HTTP 200，用 code 表达业务结果

**背景**：业务失败（手机号已注册、密码错误）如果用 4xx 返回，会和真正的服务器故障混在一起。

**决策**：所有接口一律返回 HTTP 200，响应体用 `{code, message, data}`；`code != 0` 表示业务失败。

**理由**：
- HTTP 状态码回答的是「这次请求有没有被服务器正常处理完」，业务是否成功应由业务层表达
- 业务失败返回 5xx 会污染监控告警：一个用户输错密码就产生一条告警

**权衡**：客户端必须判断 `code` 而不是状态码；Swagger 里看到 200 不代表业务成功。

---

## 2. 统一响应格式 `{code, message, data}`

**决策**：成功和失败共用同一个外壳，由 `core/response.py` 的 `success()` / `fail()` 产出。

**理由**：前端只写一套解析逻辑。`code` 用于程序判断，`message` 用于展示，`data` 用于取数据。

**错误码按业务域分段**：`1xxx` 通用 / `2xxx` 用户 / `3xxx` 商品 / `4xxx` 订单。看 code 就知道是哪个域的问题，新增错误码也不会撞车。

---

## 3. 登录失败时，用户不存在和密码错误返回同一句话

**背景**：如果「手机号未注册」和「密码错误」返回不同提示，攻击者可以拿手机号列表逐个试，靠提示差异**批量判断哪些号注册过**（用户枚举攻击）。

**决策**：两种情况合并成一个判断、同一句 `message`、同一个 code。

**权衡**：牺牲一点用户体验（用户不知道自己是不是号码填错了），换来防枚举。真实系统通常再叠加短信验证码与登录失败次数限制。

---

## 4. JWT 的 payload 是公开的，只放 user_id 和过期时间

**背景**：JWT 的 payload 只是 base64 编码，**不是加密**。任何人拿到 token 都能解出里面的内容。

**决策**：payload 只放 `sub`（user_id）和 `exp`，不放手机号、密码等敏感信息。安全性完全依赖**签名** —— 签名防的是篡改，不是偷看。

**验证方式**：把 token 中间那段 base64 解开，就能看到明文。

---

## 5. 签发 token 放在路由层，不放在 service 层

**决策**：service 只回答「你是谁、合不合法」并返回 User 对象；**签发 token 是路由层的职责**。

**理由**：service 的边界是业务规则，「发 HTTP 凭证」是接口层的事。保持 service 只返回 User，它就能被别的场景复用（改密码后重新签发、refresh token 续期），那些场景的签发时机和携带声明都不一样。若 service 直接返回 token，就被焊死在「登录接口」这一个场景上。

---

## 6. 局部更新用 PATCH，且必须 `exclude_unset`

**背景**：PATCH 的语义是「只改客户端传了的字段」。如果无脑把所有字段写回对象，客户端没传的字段会被当成「要改成 None」写进库（列是 NOT NULL 就直接炸）。

**决策**：service 里用 `model_dump(exclude_unset=True)`，只取客户端**真正传过**的字段。

**关键区分**：
- `{}` 什么都没传 → `exclude_unset=True` 得到 `{}`，一个字段都不动
- `{"nickname": ""}` 传了空串 → 得到 `{"nickname": ""}`，这是「显式清空」

**结论**：**「没传这个字段」和「传了空值」是两件不同的事。**

---

## 7. 资源归属必须从凭证推导，不能由客户端指定

**背景**：改个人资料如果用 `PUT /users/{user_id}`，客户端把 user_id 改成别人的，就改了别人的资料（**水平越权 / IDOR**）。

**决策**：`PATCH /api/v1/users/me` —— 路径里不出现 user_id，「改谁」从 token 里解出来。

**理由**：**资源归属只能从凭证推导。** 后台管理类接口才需要显式传 user_id 加角色校验，那是垂直越权的另一套问题。

---

## 8. 分类用 `parent_id` 自关联存一棵树

**决策**：分类只有一张表，每行记录「我的父分类是谁」：`parent_id` 为 NULL = 一级分类；指向某个 id = 它的子分类。外键**指向自己这张表**（自关联）。

**理由**：
- 支持**任意层级**，加减层级不用改表结构
- 一张表存完，查询简单

**派生规则**：某分类是几级 = 沿 `parent_id` 往上数到 NULL 的步数。**id 的大小和层级无关**（id 只是自增流水号，还会有空洞）。

**同类场景**：评论回复、后台菜单、组织架构、分销关系，都是这个套路。

---

## 9. 唯一索引对 NULL 不生效，一级分类的重名只能靠应用层

**实测结论**（同一个 `uq_categories_parent_id (parent_id, name)` 唯一索引）：
- `(strig, 1)` 重复 → **数据库拦住**（MySQL 错误 1062）
- `(string, NULL)` 重复 → **数据库放行**

**原因**：SQL 里 NULL 不等于 NULL，唯一索引不把多个 NULL 视为重复。

**后果**：一级分类（parent_id 为 NULL）的重名，数据库兜不住，只能靠应用层查重，而查重有并发窗口。

**彻底堵住的解法**（面试可讲）：在生成列 `COALESCE(parent_id, 0)` 上建唯一索引，或引入一个「虚拟根节点」让所有一级分类指向它。

---

## 10. 查重 + IntegrityError 兜底，是两道闸门

**背景**：插入前先查重是常规做法，但「查重」与「INSERT」之间存在时间窗口 —— 两个并发请求可能同时通过查重。

**决策**：两道闸门都要有。

| 闸门 | 位置 | 作用 | 覆盖场景 |
| --- | --- | --- | --- |
| 查重 | INSERT 之前 | 给出准确提示，省掉一次无效写库 | 正常重复 |
| `except IntegrityError` | INSERT 时 | 把数据库约束冲突翻译成业务错误，避免 500 | 并发 |

**为什么两处用同一个 code 和同一句 message**：从用户视角这是同一个错误，而且不该暴露「是数据库拦下的」这种内部细节。

## 11. 金额用 `Decimal` / `NUMERIC(10,2)`，绝不用 float

**背景**：`0.1 + 0.2` 在 Python 里等于 `0.30000000000000004`。float 是二进制浮点，很多十进制小数无法精确表示，金额累加会攒出误差。

**决策**：
- 数据库列用 `NUMERIC(10,2)`（MySQL 的 DDL 里显示为 `DECIMAL(10,2)`）
- Python 侧用 `decimal.Decimal`

**注意**：`sqlalchemy` 的 `NUMERIC` / `DECIMAL` 是**列类型**（给 `mapped_column` 用）；Pydantic 的出入参模型里必须写 Python 的 `Decimal`。两者不能混用 —— 在 schema 里写 SQLAlchemy 的类型会直接报 `PydanticSchemaGenerationError`。

## 12. 价格与库存只存 SKU，SPU 不带价格

**背景**：同一款商品不同规格价格不同（256G 卖 7999、512G 卖 8999），库存也是每个规格独立的。

**决策**：
- `price` 和 `stock` 只存在 `skus` 表
- `spus` 表不带任何价格字段
- 列表页需要「起售价」时，用 `min(sku.price)` 聚合算

**理由**：价格和库存都是**规格级**属性，挂在 SPU 上表达不了。如果 SPU 也存一份，就有两份真相（双写），不一致时不知道该信谁。

**关键**：「起售价」是**派生值，不落库**。要用就现算，真要优化再加缓存，但不能把它当成第二个真相存起来。

**权衡**：有些系统会在 SPU 上冗余一个「展示价」字段，纯粹为了列表页少一次聚合。那是**性能换一致性**，必须有机制保证派生值同步更新。

---

## 13. M3.2：SPU 与 SKU 在同一事务中一起创建

**决策**：
- 一次请求带一个 `skus` 数组（至少 1 个），SPU 和它的 SKU 一起建
- 同一事务：`add(spu)` → `await db.flush()` 拿到 `spu.id` → 回填每个 `sku.spu_id` → `add(...)` → 最后统一 `commit`

**为什么用 flush 而不是 commit**：
- `flush()` 把 SQL 发到数据库（此时能拿到自增 id），但**不结束事务**
- `commit()` 才是一锤定音
- 「先拿主键、再填外键」的场景必须用 flush，否则中途 commit 会把半成品暴露出去

**意义**：这是「一张主表 + 多张从表一起写」的最小练习；M5 下单（订单 + 订单明细 + 扣库存）是它的放大版。

---

## 14. 自增主键会有空洞，不能用它表达任何业务含义

**现象**：库里 4 行数据，但下一个自增值是 7 —— id 5、6 被「吃掉」了。

**原因**：InnoDB 在 INSERT 时会先申请自增号，再去检查约束。**约束失败或事务回滚，这个号不会归还。**

**结论**：
- **不要用 id 的连续性推断业务**（比如「id 连续说明没丢数据」是错的）
- **不要用 id 的大小表达顺序或层级**（层级看 `parent_id`，排序看 `sort`）
